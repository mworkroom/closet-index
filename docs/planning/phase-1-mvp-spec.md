## 1. 문서의 역할

이 문서는 Phase 1 구현자가 추가 제품 결정을 임의로 내리지 않고 구현·검증할 수 있게 만드는 실행 명세다.

문서 간 책임은 다음과 같다.

| 문서 | 소유하는 내용 |
|---|---|
| Roadmap | 전체 단계, 각 Phase의 목표와 종료 조건 |
| Product Plan | 제품 목적, 불변 규칙, 전체 범위와 비목표 |
| Phase 1 MVP Spec | Phase 1의 화면, 동작, 데이터, 이전, 보안, 테스트 |

이 문서에서 `확정`으로 표시한 내용은 Phase 1의 기준선이다. `미확정` 항목은 구현자가 관습이나 추측으로 채우지 않는다.

## 2. 현재 결정 상태

### 확정

- Phase 1A와 Phase 1B의 화면 목록
- 5개 하단 내비게이션
- Home을 `오늘 뭐 입지?` 흐름으로 사용
- 흰색·회색·검은색 중심의 미니멀 UI
- 옷 이미지와 색상 스와치만 데이터 색상을 사용
- Notion 커스텀 아이콘은 HEX 팔레트로 변환
- 앱 런타임은 색상 스와치를 CSS로 그리며 아이콘 이미지를 요청하지 않음
- Phase 1B는 Phase 1A와 같은 화면 구조에 대표 이미지를 추가
- 이미지 등록·새 아이템·새 착장 관리 UI는 Phase 1 범위에서 제외
- Outfit Rating은 `Favorite > OK > Error`의 서로 배타적인 품질 상태로 유지
- 하루에 같은 Outfit을 포함한 여러 Wear Log 허용
- Item 상세에서 비·장거리 걷기 적합성만 최소 편집 허용
- 개발 중 Notion을 원본으로 유지하고 전환 직전 추가 기록을 수동 이전
- `mworkroom`의 전용 workspace `000…0003`과 `closet_*` 데이터 모델
- 최종 Supabase 테이블·컬럼·relation과 workspace-consistent foreign key
- 모든 public 앱 테이블의 RLS와 최소 권한
- 같은 폼 재시도만 막는 `submission_token` 멱등 규칙
- 설명 가능한 추천 온도 범위와 단계·정렬 규칙
- Notion API snapshot → dry-run → 명시적 Supabase 적용 도구
- Phase 1A 전체 수용 체크리스트

### 미확정

- Notion 커스텀 아이콘별 최종 HEX 목록
- 이미지 파일 규격과 고정 슬롯의 정확한 좌표
- Phase 1B Storage bucket과 객체 정책
- Google OAuth 운영 redirect URL
- 실제 Notion snapshot·시험 이전·원본 전환일

## 3. 핵심 사용자 흐름

```text
로그인
→ HOME에서 외출 조건 입력
→ 기존 착장 추천 결과 확인
→ Outfit 상세에서 구성·근거·경고 확인
→ 오늘 입기
→ 착용 기록 저장
→ Calendar와 Statistics에 반영
```

탐색 흐름:

```text
CLOSET → Item 상세
LOOKBOOK → Outfit 상세
FAVORITE → Favorite Outfit 상세
MORE → Calendar / Statistics / Settings
```

## 4. 시각 디자인 기준

### 4.1 참고 방향

과거 사용 앱의 `HOME`, `CLOSET`, `LOOKBOOK`, `FAVORITE`, `MORE` 구조를 주 참고 방향으로 사용한다.

그 앱에서 유지할 특성:

- 크고 굵은 상단 제목
- 넉넉한 흰색 여백
- 검은색 선형 아이콘
- 현재 하단 탭의 채워진 검은색 아이콘
- 연한 회색 검색·입력 영역
- 단순한 목록과 3열 이미지 그리드
- `MORE`의 흰색 목록 카드

그대로 가져오지 않을 특성:

- 쇼핑과 광고 콘텐츠
- 장식용 컬러 원형 버튼
- Phase 1 범위 밖의 Packing, Customize, Backup, Help
- 기능이 없는 장식 버튼

### 4.2 색상 원칙

- 앱 배경과 surface는 흰색과 연한 회색을 사용한다.
- 제목, 본문, 아이콘, 주요 버튼은 검은색과 짙은 회색을 사용한다.
- 보조 설명, 비활성 상태, 구분선은 중립 회색을 사용한다.
- 브랜드용 강조색은 Phase 1에 도입하지 않는다.
- 실제 옷 이미지와 아이템 식별용 스와치만 데이터 색상을 사용한다.
- 흰색·아이보리 스와치는 배경과 구분되는 중립색 테두리를 가진다.
- 경고와 오류의 상태색은 의미 전달에 필요한 최소 범위에서만 사용하고, 색상만으로 상태를 전달하지 않는다.

정확한 UI용 HEX와 명도 대비는 와이어프레임·접근성 검증 후 확정한다.

### 4.3 정보 밀도

- 한 화면의 주요 행동은 한두 개만 강조한다.
- 전체 옷 색상을 큰 장식 면적으로 반복하지 않는다.
- Phase 1A 목록에서는 작은 스와치와 텍스트를 사용한다.
- Phase 1B 이미지 그리드에서도 배경과 UI chrome은 무채색을 유지한다.
- 추천 결과는 처음에 핵심 근거만 보여주고 세부 이력은 Outfit 상세에서 제공한다.

### 4.4 모바일 기준

- iPhone Safari와 PWA를 우선한다.
- 하단 내비게이션은 고정하되 콘텐츠와 폼 버튼을 가리지 않는다.
- 터치 대상은 한 손 사용에 충분한 크기를 확보한다.
- 상단 제목, 검색·필터, 콘텐츠, 하단 탭의 순서를 화면 전반에서 일관되게 유지한다.

## 5. 색상 스와치 규칙

### 5.1 원본과 이전

- 각 Notion 아이템 페이지의 커스텀 아이콘 ID를 원본 추적 정보로 읽는다.
- `Notion 커스텀 아이콘 ID → 표시 이름 → HEX` 변환표를 만든다.
- 같은 아이콘 ID는 같은 팔레트 항목에 연결한다.
- 색상 스와치는 아이템 식별용 시각 정보이며 추천 점수에는 직접 사용하지 않는다.
- 원본 아이콘 이미지는 필요하면 이전 검증용 로컬 백업으로만 보존한다.

### 5.2 앱 런타임

- 앱은 Notion 아이콘 URL을 직접 사용하지 않는다.
- Supabase Storage에 색상 아이콘 이미지를 업로드하지 않는다.
- 앱은 저장된 HEX를 이용해 CSS 원형 또는 사각형 스와치를 그린다.
- 이미지 요청 실패라는 상태가 생기지 않도록 색상 스와치는 데이터 응답만으로 표시한다.
- 스와치에는 색상명 또는 아이템명을 이용한 접근 가능한 텍스트가 있어야 한다.

### 5.3 두 종류의 색상

| 값 | 역할 | 예시 |
|---|---|---|
| 표시 스와치 | J가 아이템을 빠르게 식별하는 정확한 대표색 | `#6E347D` |
| 의미상 색상 카테고리 | 검색·필터·통계에 사용하는 넓은 분류 | `Purple` |

표시 스와치가 다르더라도 의미상 색상 카테고리는 같을 수 있다.

## 6. 전역 내비게이션

하단 탭은 다음 5개로 고정한다.

| 순서 | 탭 | 역할 | 선택 상태 |
|---:|---|---|---|
| 1 | HOME | 오늘 뭐 입지? 조건 입력과 추천 | 채워진 Home 아이콘 |
| 2 | CLOSET | 전체 아이템 탐색 | 채워진 Clothing 아이콘 |
| 3 | LOOKBOOK | 전체 착장 탐색 | 채워진 Book 아이콘 |
| 4 | FAVORITE | Favorite 착장 탐색 | 채워진 Heart 아이콘 |
| 5 | MORE | 기록·통계·설정 진입 | 채워진 Profile 또는 More 아이콘 |

규칙:

- `FAVORITE`는 별도 데이터 구조가 아니라 Favorite 필터가 적용된 Lookbook 화면을 재사용한다.
- 상세 화면과 착용 기록 화면에서는 하단 탭을 유지할지 숨길지 와이어프레임에서 검증하되, 저장 버튼이 가려지면 안 된다.
- 뒤로 가기는 사용자가 진입한 목록과 필터 상태를 보존한다.

## 7. Phase 1A 화면 목록

Phase 1A는 실제 옷 이미지 없이 데이터·추천·기록의 정확성을 검증한다.

| ID | 화면 | 유형 | 주요 책임 |
|---|---|---|---|
| A-01 | Login | 전체 화면 | Google 로그인과 허용 계정 검사 |
| A-02 | HOME — 오늘 뭐 입지? | 하단 탭 | 조건 입력, 추천 실행, 후보 표시 |
| A-03 | CLOSET | 하단 탭 | 전체 아이템 검색·필터·탐색 |
| A-04 | Item 상세 | 상세 화면 | 아이템 상태와 사용 이력 확인 |
| A-05 | LOOKBOOK | 하단 탭 | 전체 착장 검색·필터·탐색 |
| A-06 | FAVORITE | 하단 탭 | Favorite 착장만 탐색 |
| A-07 | Outfit 상세 | 상세 화면 | 구성 아이템, 추천 근거, 과거 기록 확인 |
| A-08 | 착용 기록 | 전체 화면 폼 | 선택한 Outfit의 실제 착용 저장 |
| A-09 | MORE | 하단 탭 | Calendar, Statistics, Settings 진입 |
| A-10 | Calendar / 착용 기록 | 목록·달력 화면 | 날짜별 착용 이력 확인 |
| A-11 | Statistics | 요약 화면 | 기본 착용 통계와 이전 검증 |
| A-12 | Settings | 설정 화면 | 계정 정보와 로그아웃 |

### 7.1 A-01 Login

입력:

- Google 로그인

출력:

- 허용 계정이면 HOME으로 이동
- 허용되지 않은 계정이면 데이터 접근 없이 안내

상태:

- 로그인 처리 중
- 로그인 취소
- 인증 실패
- 허용되지 않은 계정

### 7.2 A-02 HOME — 오늘 뭐 입지?

입력:

- 출발 온도: 섭씨 정수, 필수
- 귀가 온도: 섭씨 정수, 선택
- 비: `해당 없음`, `해당`
- 오래 걷기: `해당 없음`, `해당`
- 장소: 기존 Notion 선택지를 이전한 고정 목록
- 교통수단: 기존 Notion 선택지를 이전한 고정 목록

출력:

- 추천 단계
- 추천 근거
- 출발·귀가 위험 경고
- 정렬 결과 상위 3개의 Outfit 후보
- 오늘 온도 근거와 맞는 최근 구매 착장. 대표 구매일 계산에서 `Innerwear`, `Socks`, `Acc-Neck`, `Acc-Head-made`, `Acc-Hands-made`는 제외하고 `Acc-Neck-made`는 포함
- 착용 기록 0회 Outfit을 분리한 `새 착장 시험해보기`
- 전체 후보를 여는 `더 보기`

초기 상태:

- 조건 입력과 하나의 명확한 `착장 찾기` 행동을 우선 표시

빈 상태:

- 조건에 맞는 후보가 없으면 조건을 완화할 수 있는 정보와 전체 Lookbook 진입을 제공

오류 상태:

- 추천 query 실패
- 필수 입력 누락
- 비정상 온도 범위

### 7.3 A-03 CLOSET

입력:

- 검색어
- 카테고리
- 의미상 색상 카테고리
- Retired 포함 여부

출력:

- 작은 HEX 스와치
- 아이템명
- 카테고리
- Retired 상태

표현:

- Phase 1A는 451개 항목을 읽기 쉬운 목록 또는 조밀한 텍스트 카드로 표시한다.
- 큰 색상 블록을 반복하지 않는다.

빈 상태:

- 검색·필터 결과 없음

오류 상태:

- 아이템 목록을 불러오지 못함

### 7.4 A-04 Item 상세

출력:

- 아이템명
- 표시 스와치와 의미상 색상
- 카테고리
- Retired
- 비·걷기 적합성
- 포함된 Outfit
- 착용 횟수
- 마지막 착용일

편집:

- 비 적합성: 모든 Item을 기본 `가능`으로 보고, 예외 Item만 `불가`로 지정
- 장거리 걷기 적합성: 신발만 검사하며 기본 `가능`으로 보고, 예외 신발만 `불가`로 지정
- 위 두 조건 외의 Item 속성은 Phase 1에서 편집하지 않는다.

Phase 1 비노출:

- Replacement Line 편집
- 이미지 등록·교체
- 아이템 생성·삭제

빈 상태:

- 포함된 Outfit 없음
- 착용 이력 없음
- 비 또는 장거리 걷기 불가 예외 없음

오류 상태:

- 존재하지 않거나 접근할 수 없는 Item

### 7.5 A-05 LOOKBOOK

입력:

- 검색어
- 계절
- Favorite
- 최근 미착용
- 온도 범위
- 장소
- 사용 불가 착장 포함

출력:

- Outfit fallback 카드
- 구성 아이템명과 스와치
- Rating
- 마지막 착용일
- 착용 횟수

표현:

- 실제 착장 이미지가 없을 때도 카드 높이와 이동 동작이 안정적이어야 한다.
- 착장명은 선택 정보이며, 이름이 없으면 짧은 아이템 조합 문구를 표시한다.
- Rating이 `Error`이거나 Retired Item을 포함한 Outfit은 기본 목록에서 숨긴다.
- `사용 불가 착장 포함`을 켜면 숨겨진 Outfit을 확인할 수 있다.

빈 상태:

- 필터 결과 없음
- 아직 검증된 착장 없음

오류 상태:

- Outfit 목록을 불러오지 못함

### 7.6 A-06 FAVORITE

- A-05 LOOKBOOK을 재사용한다.
- `Rating = Favorite` 필터는 고정되어 있으며 사용자가 현재 범위를 명확히 알 수 있어야 한다.
- Favorite 결과가 없으면 전체 Lookbook으로 이동할 수 있다.

### 7.7 A-07 Outfit 상세

출력:

- Outfit 식별 정보
- 전체 구성 아이템
- Rating (`Favorite`, `OK`, `Error`, 미입력)
- 착용 횟수와 마지막 착용일
- OK·추움·더움 관측
- 장소와 교통수단 이력
- HOME 조건에서 진입한 경우 현재 추천 근거와 경고

주요 행동:

- `오늘 입기`

빈 상태:

- 착용 이력 없음

### 7.8 A-08 착용 기록

입력:

- 선택된 Outfit
- 날짜: 한국 시간 기준 날짜, 기본값은 오늘
- 출발 온도: 섭씨 정수
- 귀가 온도: 섭씨 정수, 선택
- 출발·귀가 체감: 각각 `추움`, `OK`, `더움`
- 장소: 기존 Notion 선택지를 이전한 고정 목록
- 교통수단: 기존 Notion 선택지를 이전한 고정 목록
- 메모

출력:

- 새 Wear Log
- 갱신된 Outfit·Item 통계

규칙:

- Outfit relation은 현재 선택값으로 고정하고 이름 문자열로 다시 찾지 않는다.
- HOME에서 입력한 조건은 가능한 범위에서 미리 채운다.
- 각 Wear Log는 독립된 UUID를 가진다.

- 저장 성공 전 동일한 폼 제출의 반복만 막고, 과거 기록과 값이 같다는 이유로 새 기록을 거부하지 않는다.

- 저장 실패
- 통계 갱신 검증 실패

## 8. Phase 1B 화면 목록

Phase 1B는 별도의 앱 구조를 만들지 않는다. A-01부터 A-12까지 동일한 화면과 이동을 유지하며 다음 표현을 추가한다.

| 대상 화면 | Phase 1B 변경 |
|---|---|
| HOME | 추천 후보에 대표 착장 합성 이미지 표시 |
| CLOSET | 이미지가 준비된 Item은 이미지 카드, 나머지는 HEX 스와치 fallback |
| Item 상세 | 준비된 누끼 이미지 표시 |
| LOOKBOOK | 대표 착장을 3열 이미지 카드로 비교 |
| FAVORITE | LOOKBOOK과 같은 이미지 카드 표현 |
| Outfit 상세 | 착장 합성 이미지와 구성 Item 이미지 표시 |
| Calendar | 이미지가 있는 Outfit은 작은 착장 미리보기 표시 |

Phase 1B의 완료 조건:

- 이미지가 있는 항목과 없는 항목이 같은 목록에서 깨지지 않는다.
- 이미지 추가 전후로 화면의 정보 구조와 주요 행동이 바뀌지 않는다.
- 옷 이미지가 많아져도 UI chrome은 무채색을 유지한다.
- 흔히 사용하는 온도대에서 여러 시각적 후보를 빠르게 비교할 수 있다.
- 추천 후보 선택부터 착용 기록까지 모바일에서 반복 사용할 수 있다.

## 9. 공통 상태와 동작

### Loading

- 목록과 상세는 레이아웃이 크게 움직이지 않는 중립색 skeleton을 사용한다.
- 저장·수정·삭제 중에는 동일 요청의 중복 제출을 막고 진행 상태를 표시한다.

### Empty

- 정상적인 빈 상태와 오류를 구분한다.
- 필터 결과 없음에는 필터 초기화 행동을 제공한다.
- 이력 없음에는 `아직 기록 없음`처럼 사실만 표시하고 값을 추정하지 않는다.

### Error

- 데이터 불러오기 실패, 저장 실패, 권한 없음, relation 손상을 구분한다.
- 오류 때문에 원본 값이 사라지거나 기본값으로 덮어써지지 않는다.
- 재시도가 안전한 경우에만 재시도 행동을 제공한다.

### Navigation

- 목록에서 상세로 이동했다가 돌아오면 검색어·필터·스크롤 위치를 가능한 범위에서 보존한다.
- 같은 이름의 Outfit이 있어도 UUID로 올바른 상세를 연다.
- 하단 탭은 현재 위치를 명확히 표시한다.

## 11. 화면 수용 기준

- 첫 로그인 후 HOME까지 막힘없이 진입한다.
- HOME에서 조건 입력 후 추천 후보와 근거를 확인한다.
- HOME은 상위 3개 후보를 먼저 표시하고 `더 보기`로 전체 후보를 연다.
- HOME은 착용 기록 0회 Outfit을 `새 착장 시험해보기`로 분리하고, 첫 Wear Log 저장 후 기록 기반 추천으로 자동 전환한다.
- 추천 후보에서 정확한 Outfit 상세가 열린다.
- `오늘 입기`로 생성한 Wear Log가 Calendar와 Statistics에 반영된다.
- 같은 날짜와 같은 Outfit으로 여러 Wear Log를 저장해도 각 기록이 독립적으로 유지된다.
- Calendar에서 Wear Log를 수정·삭제하면 관련 통계가 일관되게 다시 계산된다.
- CLOSET의 모든 Item은 실제 옷 이미지 없이도 이름과 HEX 스와치로 식별할 수 있다.
- Item 상세에서 비·장거리 걷기 적합성만 수정할 수 있다.
- LOOKBOOK의 모든 Outfit은 이미지 유무와 관계없이 열 수 있다.
- Error·Retired 포함 Outfit은 기본 Lookbook에서 숨겨지고 필터를 켜면 확인할 수 있다.
- FAVORITE는 LOOKBOOK과 결과·상세 동작을 공유한다.
- 5개 하단 탭의 활성 상태가 정확하다.
- 하단 내비게이션이 콘텐츠와 저장 버튼을 가리지 않는다.
- 흰색·아이보리 스와치도 배경과 구분된다.
- 색상 없이도 텍스트와 아이콘으로 상태를 이해할 수 있다.

## 12. 확정된 원본 전환 운영 원칙

```text
개발 중 Notion 원본과 실제 기록 유지
→ Supabase 시험 이전과 Technical Alpha 검증
→ Technical Alpha에서 생성한 Supabase Wear Log는 테스트 데이터로 취급
→ 전환 직전 Notion에 추가된 기록을 J가 Supabase에 수동 이전
→ 원본과 Supabase 최종 대조
→ 전환 시점 선언
→ 이후 앱과 Supabase에만 기록
→ Notion 읽기 전용 보관
```

- 개발 기간에 Notion 입력을 중단하지 않는다.
- 지속적인 양방향 동기화는 구현하지 않는다.
- 전환 직전 추가분의 수동 이전 절차와 검증 항목은 원본 전환 체크리스트에서 구체화한다.
- 전환 시점을 기준으로 쓰기 원본은 항상 하나만 유지한다.
