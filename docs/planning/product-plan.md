- 최종 수정일: 2026-07-26
- 문서 상태: 제품 기준선

## 1. 문서의 역할

이 문서는 Closet Index가 왜 존재하고, 어떤 현실 규칙을 보존하며, 전체 Roadmap에서 무엇을 만들 것인지 정하는 제품 기준 문서다.

이 문서가 소유하는 내용:

- 제품의 목적과 핵심 성공 기준
- 현재 Notion에서 확인한 데이터 의미
- 착장·착용 기록·추천의 불변 규칙
- 데이터 이전과 원본 전환 원칙
- 전체 기능 범위와 비목표
- Phase별 제품 경계

이 문서가 소유하지 않는 내용:

- 최종 SQL과 migration 파일
- 화면별 상세 레이아웃
- 추천 점수의 세부 가중치
- API 요청·응답 형식
- 테스트 코드와 배포 명령

위 구현 세부사항은 별도의 `phase-1-mvp-spec.md`에서 확정한다.

## 2. 제품 정의

### 한 문장 정의

> 과거의 내가 실제로 입고 검증한 착장을, 오늘의 조건에 맞춰 빠르게 다시 찾는 개인용 기온 기반 Lookbook.

### 해결하려는 문제

현재 Notion은 데이터의 안정성, relation, rollup, formula, 착용 통계에는 강하다. 하지만 오늘 입을 옷을 고르기 위해 저장된 착장을 빠르게 훑고 비교하는 경험은 부족하다.

과거에 사용한 옷장 앱은 종이 인형처럼 옷을 조합하고 이미지로 착장을 탐색하는 경험이 좋았다. 반면 데이터가 꼬였을 때 다른 항목이 열리는 문제가 있었고 통계가 빈약했다.

Closet Index는 두 시스템의 장점을 결합한다.

- Notion에서 검증된 데이터 관계와 통계
- 과거 앱에서 유용했던 이미지 중심 탐색
- 실제 온도와 체감 기록에 근거한 설명 가능한 추천

### 핵심 사용 장면

```text
오늘 외출 조건을 입력한다
→ 조건에 맞는 기존 착장을 빠르게 훑는다
→ 추천 근거와 주의사항을 확인한다
→ 한 착장을 선택한다
→ 실제 착용 기록을 남긴다
→ 다음 추천과 통계에 반영된다
```

## 3. 사용자와 사용 환경

### 사용자

- 최종 사용자는 J 한 명이다.
- 가족 계정, 다중 사용자 협업, 공개 서비스는 초기 범위가 아니다.
- J가 직접 사용하며 결과의 이상 여부를 판단하고 규칙을 수정할 수 있다.

### 사용 환경

- iPhone 중심의 모바일 사용
- 개인용 웹앱 또는 PWA
- 짧은 외출 준비 시간에 한 손으로 빠르게 탐색
- PC에서는 데이터 관리와 이미지 등록 보조

### 인증

- Google 로그인을 사용한다.
- J의 허용된 계정만 앱 데이터에 접근할 수 있다.
- 로그인 여부만 확인하는 것으로 끝내지 않고, 모든 사용자 데이터에 소유자 기준 접근 제어를 적용한다.

## 4. 목표와 성공 기준

### 제품 목표

1. 오늘 조건에 맞는 기존 착장을 빠르게 찾을 수 있다.
2. 추천 결과가 왜 나왔는지 이해할 수 있다.
3. 선택한 착장을 최소 입력으로 기록할 수 있다.
4. 착장과 개별 아이템의 착용 통계를 정확히 유지한다.
5. 실제 옷 사진이 없는 상태에서도 HEX 색상 스와치로 식별할 수 있고, 이미지가 추가될수록 탐색 경험이 좋아진다.
6. Notion에서 쌓은 과거 기록과 relation을 잃지 않는다.

### v1.0 성공 기준

- 수동 출발 온도와 선택적 귀가 온도로 후보를 찾을 수 있다.
- 평균 온도를 중심으로 추천하되 출발·귀가 온도 위험을 따로 알린다.
- 현재 계절의 대표 착장 20~30개를 이미지 카드로 비교할 수 있다.
- 이미지 없는 착장도 HEX 색상 스와치와 아이템 조합으로 계속 사용할 수 있다.
- 착장 선택과 착용 기록이 통계에 정확히 반영된다.
- Notion 표본과 전체 집계 기준으로 relation·착용 횟수·마지막 착용일이 일치한다.
- 같은 이름의 서로 다른 착장이 병합되지 않는다.
- 실제 생활에서 핵심 흐름을 반복 사용해도 막히는 문제가 없다.

## 6. 제품 원칙

### 6.1 과거에 검증된 착장을 다시 찾는다

AI가 새로운 스타일을 창작하는 것이 핵심이 아니다. 실제로 입은 기록과 체감을 우선한다.

### 6.2 제품 규칙을 임의로 보충하지 않는다

요구사항의 빈칸은 일반적인 옷장 앱의 관습으로 자동 결정하지 않는다. 구현 전에 `Open Decisions`로 남기고 실제 사례로 판단한다.

### 6.3 저장값과 계산값을 구분한다

직접 입력한 값, 이전한 원본 값, API가 제공한 값, 계산된 통계를 구분한다. 계산 결과의 원본과 계산 방법을 추적할 수 있어야 한다.

### 6.4 추천은 설명 가능해야 한다

사용자에게 점수만 보여주지 않는다. `27°C에서 OK 2회`, `귀가 예상 온도에서는 추울 수 있음`처럼 근거를 함께 보여준다.

### 6.5 과거 사실을 현재 상태로 덮어쓰지 않는다

Retired 아이템과 과거 착장은 기록에서 보존한다. 현재 추천에서 제외하는 것과 과거 기록을 삭제하는 것은 다른 행동이다.

### 6.6 이미지 준비가 데이터 사용을 막지 않는다

누끼 이미지가 없는 항목도 정상 데이터다. 이미지 등록은 현재 계절의 대표 착장부터 점진적으로 진행한다.

### 6.7 자동화는 수동 fallback을 남긴다

날씨 API나 이미지 처리 기능이 실패해도 수동 입력과 기존 데이터 탐색을 계속 사용할 수 있어야 한다.

### 6.8 앱의 장식보다 옷을 시각적 중심에 둔다

앱 UI는 흰색·회색·검은색을 중심으로 구성한다. 장식용 강조색을 늘리지 않고, 실제 옷 이미지와 아이템 식별용 색상 스와치만 데이터 색상을 사용한다.

### 6.9 색상 식별 단서를 보존한다

J는 아이템 사진이 없는 과거 데이터도 색상 아이콘을 통해 충분히 식별할 수 있었다. 실제 옷 사진의 부재와 시각적 식별 단서의 부재를 같은 상태로 취급하지 않는다.

## 7. 현재 시스템과 데이터

### 7.1 Notion 구조

조사 시점의 주요 데이터:

| 데이터 | 규모 | 역할 |
|---|---:|---|
| Wardobe | 451개 | 개별 아이템 |
| Retired Items | 87개 | 현재 추천에서 제외할 과거 아이템 |
| Outfits | 507개 | 고정된 아이템 조합 |
| Outfit Daily Logs | 783개 | 실제 착용 기록 |
| Replacement Line | 별도 DB | 교체 계보와 스타일 연속성 |

Outfit Rating 분포:

- `OK`: 462개
- `Favorite`: 16개
- `Error`: 26개
- 미입력: 3개

relation 품질:

- 아이템 relation이 비어 있는 착장: 1개
- Outfits 유형 착용 기록 중 Outfit relation 누락: 0개
- 개별 아이템 이름 중복: 조사 범위에서 없음
- 착장명 중복: 다수 존재하지만 실제 아이템 조합이 다른 사례가 포함됨

### 7.2 Daily Log의 실제 의미

Daily Log는 옷 전용 DB가 아니라 여러 개인 활동을 함께 기록하는 공용 DB다.

Closet Index 이전 대상:

- `Category = Outfits`인 기록

Closet Index 이전 비대상:

- Cinema
- Movie
- TV
- Book
- Comics
- Knitting
- Astrology
- 그 밖의 옷과 무관한 기록

착용일은 최근 기록에서 `Start`가 아니라 `End`를 사용한다.

### 7.3 온도 공백의 실제 의미

`Temp Back`이 비어 있는 이유는 대부분 출발과 귀가 온도가 같기 때문이다. 이를 실제 결측치로 처리하지 않는다.

```text
Notion Temp Out = 18
Notion Temp Back = 공백

→ temp_out = 18
→ temp_back = 18
→ temp_back_inferred = true
```

`Temp Out` 자체가 비어 있는 기록은 실제 온도 미상이다.

- 착용 횟수와 마지막 착용일에는 포함
- 온도 추천 학습에는 사용하지 않음
- 임의의 평균값이나 계절값을 넣지 않음

### 7.4 이미지 상태

- 현재 Notion에는 실제 아이템 사진이나 착장 콜라주가 없다.
- 각 아이템에는 J가 별도 업로드한 이미지 기반 Notion 커스텀 아이콘이 연결되어 있다.
- 커스텀 아이콘은 아이템을 구분하는 유효한 색상 자산이며, Notion 커스텀 아이콘 ID로 연결 관계를 추적할 수 있다.
- 앱 런타임에서는 커스텀 아이콘 이미지를 직접 불러오지 않고, 이전 시 확정한 HEX 값을 CSS 색상 스와치로 표시한다.
- 색상 스와치와 검색·필터용 의미상 색상 카테고리는 서로 다른 데이터로 취급한다.
- 과거 iPhone 앱의 이미지 원본은 이전할 수 없다.
- 새 앱의 누끼 이미지는 J가 점진적으로 새로 준비한다.

## 8. 핵심 도메인 규칙

### 8.1 착장의 동일성

착장은 고정된 아이템 집합이다.

- 아이템 하나가 달라도 별도의 착장이다.
- 기존 착장의 아이템 구성을 직접 수정하지 않는다.
- 변경이 필요하면 기존 착장을 복제한 뒤 새 착장으로 저장한다.
- 과거 Wear Log는 원래 착장 relation을 계속 유지한다.

### 8.2 착장명과 고유값

Notion에서는 제목이 필수여서 아이템 이름 일부를 조합한 임시 착장명을 사용했다. 제목이 길어지는 것을 피하기 위해 이너 등 일부 아이템은 생략됐으므로 같은 제목의 서로 다른 착장이 존재할 수 있다.

새 앱의 규칙:

- 데이터 고유값은 UUID다.
- 착장명은 고유하지 않으며 선택 정보다.
- `display_name`은 비워둘 수 있다.
- 이름이 없으면 아이템 조합을 이용해 화면용 짧은 문구를 생성한다.
- 같은 이름을 이유로 착장을 병합하지 않는다.
- 새 착장 생성 시 이름이 아니라 완전히 같은 아이템 조합의 존재 여부를 확인한다.

### 8.3 Retired

- Retired 아이템은 과거 Outfit과 Wear Log에서 보존한다.
- Retired 아이템이 포함된 착장은 현재 추천에서 기본 제외한다.
- 과거 통계와 달력에서는 계속 확인할 수 있다.

### 8.4 Outfit Rating

Outfit Rating은 착장을 입었을 때의 전체 만족도와 감정 평가다. 세 값은 서로 배타적인 품질 상태이며 선호 순서는 다음과 같다.

```text
Favorite > OK > Error
```

- `Favorite`: 드물지만 착장이 매우 마음에 들어 기분이 좋았던 상태
- `OK`: 특별한 불만 없이 일반적으로 입은 상태
- `Error`: 착장이 마음에 들지 않았거나 입었을 때 기분이 나빴던 상태
- 미입력: 아직 평가되지 않은 별도 상태

`Favorite`는 `OK + 별도 Favorite boolean`으로 분리하지 않는다. FAVORITE 화면은 `Rating = Favorite`인 Outfit을 필터링한다.

Outfit Rating의 `OK`와 Wear Log의 출발·귀가 체감 `OK`는 이름만 같고 의미가 다른 값이다. 전자는 착장 전체에 대한 평가이고, 후자는 특정 온도에서 춥거나 덥지 않았다는 관측이다. 데이터 모델과 추천 계산에서 두 값을 섞지 않는다.

Rating이 `Error`인 착장은 현재 추천과 기본 Lookbook에서 제외하지만 데이터와 과거 기록은 삭제하지 않는다. 별도의 `사용 불가 착장 포함` 필터를 사용하면 확인할 수 있다.

### 8.5 Replacement Line

- Replacement Line과 아이템 relation은 데이터 이전 대상이다.
- v1.0 UI에서는 노출하거나 편집하지 않는다.
- 교체 계보 관리 화면은 이후 Phase에서 추가한다.

### 8.6 조건 속성

`rain_ok`, `long_walk_ok`처럼 현재 Notion에 없는 속성은 세 상태를 사용한다.

- 가능
- 불가
- 미확인

미확인을 불가로 간주하지 않는다. 전체 아이템을 사전 태깅하지 않고 실제 추천 결과를 사용하면서 필요한 항목부터 입력한다.

Phase 1에서는 Item 상세에서 비·장거리 걷기 적합성만 최소 범위로 수정할 수 있다. 이미지, 카테고리, 색상 등 일반 Item 편집 기능은 이후 Phase의 범위로 남긴다.

### 9.2 Outfits

고정된 아이템 조합.

주요 개념:

- UUID
- 사용자 소유자
- Notion 원본 ID
- 선택적 표시 이름
- Rating (`Favorite`, `OK`, `Error`, 미입력)
- 생성 시각
- 현재 추천 가능 여부

### 9.3 Outfit Items

Outfit과 Item을 연결하는 다대다 relation.

주요 개념:

- Outfit UUID
- Item UUID
- 시각 합성을 위한 슬롯
- 정렬 순서
- 기본 위치와 크기
- 겹침 순서

### 9.4 Wear Logs

실제 착용 기록.

주요 개념:

- UUID
- 사용자 소유자
- Notion 원본 ID
- 착용일
- Outfit UUID
- 출발 온도
- 귀가 온도
- 추천 기준 평균 온도
- 출발·귀가 체감
- 장소
- 교통수단
- 비 등 날씨 메모
- 온도 출처와 추론 여부
- 일반 메모

Wear Log의 고유값은 UUID이며 `착용일 + Outfit` 조합을 고유값으로 사용하지 않는다. 하루에 서로 다른 Outfit 여러 개와 같은 Outfit 여러 개를 모두 기록할 수 있다. 시간은 필수로 저장하지 않으며, 같은 날짜의 기록은 장소와 교통수단을 포함한 각 기록의 내용으로 구분한다. 시간이 없으므로 같은 날짜 기록 사이의 실제 시간순서는 보장하지 않는다.

### 9.5 Replacement Lines

아이템 교체 계보와 스타일 연속성을 보존하는 구조.

v1.0에서는 이전과 relation 보존만 수행하며 화면은 제공하지 않는다.

### 9.6 Images

아이템 누끼 이미지와 합성 결과.

주요 개념:

- Storage 객체 경로
- 원본 또는 누끼 구분
- 처리 상태
- 이미지 크기
- 합성용 기본 배치
- 캐시된 Outfit 미리보기

### 9.7 계산 결과

다음 값은 원본으로 직접 입력하기보다 원본 relation과 Wear Log에서 계산한다.

- 착장 착용 횟수
- 아이템 착용 횟수
- 마지막 착용일
- 온도 적합 범위
- 현재 추천 가능 여부
- 최근 반복 착용 여부

계산이 View로 구현될 경우 사용자 소유권과 RLS를 존중해야 한다.

## 10. 추천 모델

### 10.1 목표

추천 모델은 최적의 패션을 창작하지 않는다. 현재 조건과 비슷한 상황에서 실제로 잘 입었던 착장을 먼저 보여준다.

### 10.2 Phase 1 수동 입력

입력:

- 출발 온도: 필수
- 귀가 온도: 선택
- 비: `해당 없음`, `해당`, `미지정`
- 장거리 걷기: `해당 없음`, `해당`, `미지정`
- 장소: 기존 Notion 선택지를 이전한 고정 목록에서 선택
- 교통수단: 기존 Notion 선택지를 이전한 고정 목록에서 선택

귀가 온도를 입력하지 않으면 출발 온도와 같다고 처리한다.

```text
target_temp = (temp_out + temp_back) / 2
```

### 10.3 Phase 2 날씨 자동화

J가 출발 시각과 귀가 시각을 입력하면 앱이 예보에서 두 시각의 온도를 가져온다.

- 평균 온도로 후보 순위를 정한다.
- 출발·귀가 온도는 각각 안전 경고에 사용한다.
- 예보를 불러오지 못하면 Phase 1의 수동 입력으로 돌아간다.
- 필요하면 추천 기준 온도를 수동으로 수정할 수 있다.

### 10.4 온도·체감 관측값

각 Wear Log를 `(온도, 체감)` 관측값으로 변환한다.

```text
(27, OK)
(23, 추움)
(30, 더움)
```

출발과 귀가 온도·체감이 모두 같으면 동일한 착용에서 나온 중복 관측으로 과도하게 가중하지 않는다.

온도는 같지만 체감이 다르면 두 관측을 모두 보존한다. 외출 경과나 실내 환경 때문에 체감이 달라졌을 수 있기 때문이다.

### 10.5 OK

- `OK`인 온도는 검증된 적정 온도다.
- 한 번만 `OK`였다면 기본 허용 범위는 해당 온도의 ±2°C다.
- 여러 온도에서 `OK`였다면 최저·최고 `OK` 온도와 기본 허용 폭을 이용해 검증 범위를 만든다.
- 상충하는 `추움/더움` 기록이 있으면 검증 범위를 무조건 확장하지 않고 경고와 신뢰도에 반영한다.

### 10.6 추움

`T°C에서 추움`은 다음 의미다.

- 추천 온도가 T 이하이면 감점과 경고
- 추천 온도가 T보다 높으면 이 기록만으로 부적합 판정하지 않음

### 10.7 더움

`T°C에서 더움`은 다음 의미다.

- 추천 온도가 T 이상이면 감점과 경고
- 추천 온도가 T보다 낮으면 이 기록만으로 부적합 판정하지 않음

### 10.8 출발·귀가 온도 차이

평균 온도로 후보를 정렬하되, 양 끝 온도를 별도로 평가한다.

예:

```text
출발 8°C
귀가 2°C
평균 5°C
```

5°C에 적합한 착장을 먼저 찾는다. 그러나 2°C에서 추웠던 기록이 있으면 `귀가 시 추울 수 있음` 경고를 표시한다.

평균만 사용하여 위험을 숨기지 않고, 전체 구간을 무조건 통과시키느라 후보를 모두 제거하지도 않는다.

### 10.9 추천 단계

초기 UI는 불투명한 숫자 하나보다 다음 세 단계를 우선한다.

#### 추천 높음

- 평균 온도가 검증된 OK 범위 안
- 출발·귀가 온도에서 상충하는 추움/더움 기록 없음
- Retired 또는 Error 아님

#### 추천 가능

- OK 범위에서 조금 벗어남
- 온도 근거가 적음
- 비·걷기 조건이 미확인

#### 주의

- 출발 또는 귀가 온도가 추움/더움 기록과 충돌
- 비가 오는데 포함 아이템 중 `rain_ok = 불가`
- 다른 조건은 맞지만 데이터 근거가 약함

같은 단계 안에서는 다음 요소로 정렬한다.

1. 온도 적합성
2. Outfit Rating (`Favorite` > `OK` > 미입력, `Error`는 기본 제외)
3. 같은 장소 또는 교통수단의 과거 기록
4. 착용 근거가 많은 Outfit
5. 최근 착용일
6. 비·걷기 조건 경고

정확한 수치 가중치는 Phase 1 명세서와 실제 사례 테스트에서 결정한다.

착용 기록이 없는 계획 Outfit도 유효한 후보로 유지한다. 다만 기록 기반 추천과 같은 확신도로 섞지 않고 HOME의 `새 착장 시험해보기` 영역에 분리한다. 실제로 입고 첫 Wear Log를 저장하면 자동으로 기록 기반 추천에 합류한다.

HOME은 위 정렬 결과의 상위 3개를 먼저 보여주고 `더 보기`로 전체 후보를 연다. 온도 적합성은 Outfit Rating보다 항상 먼저 평가한다.

### 10.10 추천 근거

추천 카드와 상세 화면은 최소한 다음 근거를 제공한다.

```text
추천 높음
24~27°C에서 OK 3회
CGV에서 착용 2회
마지막 착용 31일 전
```

```text
주의
평균 온도는 적합
귀가 예상 20°C — 21°C에서 추웠던 기록 있음
```

## 11. 미입력·불확실 데이터 처리

| 상태 | 처리 |
|---|---|
| 귀가 온도 공백 | 출발 온도와 동일하게 복원하고 추론 여부 기록 |
| 출발 온도 공백 | 통계에는 포함하고 온도 추천 학습에서는 제외 |
| 온도는 있으나 체감 없음 | 착용 사실만 보존하고 OK로 추정하지 않음 |
| 비 가능 여부 미확인 | 제외하지 않고 확인 필요 경고 |
| 비 불가 | 후보를 뒤로 내리고 명확한 경고 |
| 장거리 걷기 미확인 | 제외하지 않고 확인 필요 경고 |
| 실제 옷 이미지 없음 | 추천에 영향 없음, HEX 색상 스와치·아이템 목록 fallback |
| 카테고리 이상 | 이전 검증 목록에 표시하고 확인 전 자동 슬롯 확정 금지 |
| 착용 이력 없음 | 검증된 착장 뒤에 `온도 근거 없음`으로 표시 |
| Rating 미입력 | Error로 간주하지 않고 미평가 상태로 유지 |
| Rating Error | 기본 추천 제외, 별도 필터에서 확인 |
| Retired 아이템 포함 | 현재 추천 제외, 과거 기록 보존 |

미입력을 일반적인 기본값으로 조용히 바꾸지 않는다.

## 12. 이미지와 시각 탐색

### 12.1 현재 상태

실제 옷 사진과 착장 콜라주 원본은 없는 것으로 시작한다. 다만 Notion 커스텀 아이콘에 저장된 색상 정보는 이전 가능한 식별 자산으로 본다.

### 12.2 Phase 1 전략

1. 전체 Notion 데이터를 먼저 이전한다.
2. Notion 커스텀 아이콘 ID와 HEX 값의 변환표를 만들고 아이템 relation을 보존한다.
3. 앱에서는 이미지 요청 없이 CSS로 색상 스와치를 그린다.
4. 현재 계절의 대표 착장 20~30개를 고른다.
5. 그 착장에 필요한 아이템만 우선 누끼 이미지를 준비한다.
6. 고정 슬롯으로 합성하여 Outfit 카드를 만든다.
7. 실사용에서 자주 필요한 항목부터 이미지 범위를 늘린다.

원본 커스텀 아이콘 이미지는 앱 런타임 자산으로 사용하지 않는다. 필요하면 이전 검증용 로컬 백업으로만 보존한다.

## 14. 데이터 이전과 원본 전환

### 14.1 이전 원칙

- 이름을 ID로 사용하지 않는다.
- Notion 페이지 ID를 원본 추적 키로 보존한다.
- 아이템을 먼저 이전한 뒤 Outfit relation을 재구성한다.
- Outfit을 이전한 뒤 Outfits 유형 Wear Log를 연결한다.
- Replacement Line relation을 보존한다.
- formula와 rollup 결과만 복사하지 않고 가능한 경우 원본 데이터로 재계산한다.
- 원본과 계산 결과를 구분한다.

### 14.2 검증

최소 검증 항목:

- 전체 행 수
- relation 수
- relation이 비어 있는 항목
- 중복된 Notion 원본 ID
- 이름은 같지만 구성이 다른 착장
- 착장별 아이템 수
- 착장별 착용 횟수
- 아이템별 착용 횟수
- 마지막 착용일
- Retired 포함 착장
- Error 착장
- 출발·귀가 온도 변환
- 이미지 상태

### 14.3 전환

```text
개발 중 Notion 원본과 실제 기록 유지
→ Supabase 시험 이전
→ 자동 검증
→ 표본 대조
→ Technical Alpha의 Supabase 기록은 테스트 데이터로 사용
→ 전환 직전 Notion에 추가된 기록을 Supabase로 수동 이전
→ 최종 대조
→ 전환 시점 선언
→ 이후 앱과 Supabase에만 기록
→ Notion 읽기 전용 보관
→ Visual MVP 실사용과 최종 검증
```

지속적인 양방향 동기화는 구현하지 않는다.

Notion 입력을 장시간 중단할 필요는 없다. 다만 전환 직전의 수동 이전과 대조가 끝난 뒤에는 새 기록을 Notion에 추가하지 않는다. 전환 시점을 기준으로 어느 시스템이 원본인지 항상 하나로 유지한다.

## 15. 보안과 데이터 접근

### 인증

- Google 로그인
- 허용된 J의 계정만 접근

### 데이터 권한

- 모든 사용자 소유 데이터는 소유자 ID를 가진다.
- exposed table에는 RLS를 적용한다.
- 읽기·추가·수정·삭제 정책은 소유자 조건을 사용한다.
- View도 사용자 권한을 우회하지 않게 설계한다.

### 프론트엔드 키

- 공개 가능한 클라이언트 키만 사용한다.
- 서비스 역할 키와 비밀 키는 브라우저에 포함하지 않는다.

### Storage

- 아이템 이미지와 합성 이미지는 사용자 소유 경로로 분리한다.
- 읽기·업로드·교체 권한을 사용자 소유권에 맞게 설정한다.

정확한 RLS와 Storage 정책은 Phase 1 명세와 migration에서 확정하고 테스트한다.

## 16. 비기능 요구사항

### 모바일 우선

- iPhone Safari와 PWA 사용을 우선 검증한다.
- 주요 버튼은 충분한 터치 크기와 명확한 상태를 가진다.
- 하단 고정 UI가 콘텐츠나 입력을 가리지 않아야 한다.

### 시각 디자인

- 흰색 배경, 검은색 텍스트·아이콘, 연한 회색 입력·필터·구분선을 기본으로 한다.
- 큰 굵은 화면 제목, 선형 아이콘, 현재 탭의 채워진 아이콘을 사용한다.
- 옷 이외의 장식용 컬러 블록은 사용하지 않는다.
- Phase 1A는 텍스트와 작은 색상 스와치 중심, Phase 1B는 같은 구조에 대표 이미지를 추가한다.
- 흰색·아이보리처럼 배경과 구분하기 어려운 스와치에는 중립색 테두리를 제공한다.

### 신뢰성

- 하나의 화면 항목을 눌렀을 때 다른 데이터가 열리는 상태를 허용하지 않는다.
- 모든 relation은 안정적인 UUID를 사용한다.
- 데이터 변경 후 관련 통계가 일관되게 갱신돼야 한다.

### 설명 가능성

- 통계가 저장값인지 계산값인지 구분한다.
- 추천 결과에 원본 근거를 표시한다.
- 자동 추론한 값에는 출처 또는 추론 여부를 남긴다.

### 복구 가능성

- 데이터 이전은 다시 실행해도 중복되지 않아야 한다.
- 삭제보다 Retired 또는 상태 변경을 우선한다.
- 원본 전환 전까지 Notion을 복구 기준으로 유지한다.

### 성능

- 모바일 Lookbook에서 수백 개 착장을 다룰 수 있어야 한다.
- 카드 이미지와 합성 결과는 필요한 크기로 최적화하고 캐시할 수 있어야 한다.
- 통계 계산이 반복될 경우 View 또는 집계 query를 사용한다.

## 17. 전체 Roadmap 범위

### Phase 1A — Technical Alpha

- Supabase와 Google 로그인
- 데이터 이전과 검증
- 수동 조건 기반 추천
- 착장 탐색·상세·기록
- 기본 통계
- Notion 아이콘 기반 HEX 팔레트 이전
- 텍스트·색상 스와치 중심 fallback
- 5개 하단 내비게이션과 무채색 모바일 UI

### Phase 1B — Visual MVP / v1.0

- 대표 착장 20~30개 이미지
- 고정 슬롯 합성
- Phase 1A와 동일한 화면의 이미지 기반 Home·Closet·Lookbook
- 모바일 실사용
- Supabase 원본 전환

### Phase 2 — Weather Automation

- 출발·귀가 시각 예보
- 평균 온도 자동 계산
- 출발·귀가 위험 경고
- 비·눈·습도 연동
- 수동 fallback

### Phase 3 — Visual Wardrobe Expansion

- 이미지 적용 범위 확대
- 아이템 이미지 관리
- 슬롯형 코디 만들기
- 착장 복제와 미리보기 캐시

### Phase 4 — Maintenance & Insights

- Replacement Line 관리
- 세탁 기록
- 미착용·반복 착용 분석
- 알림과 고급 통계
