# Closet Index Phase 6 Care & Replenishment Plan

- 작성일: 2026-08-05
- 상태: 구현 전 최종 확정 계획
- 선행 단계: Phase 4 Replacement Line 완료
- 목적: Item 상세 페이지와 Maintenance 페이지에서 교체 계보, 재구매, 장기 미착용 점검, 특수 세탁 관리를 일관된 기준으로 제공한다.
- 관련 문서: [Roadmap](./roadmap.md), [Phase 4 Maintenance & Insights Plan](./phase-4-maintenance-insights-plan.md), [Product Plan](./product-plan.md)

> Phase 6은 한 장의 계획서 안에서 네 단계로 진행한다. 각 단계는 순서대로 구현하되, 구매·착용·관리 사건을 공통 원본으로 삼아 Item 목록, Item 상세, Maintenance 페이지가 같은 결과를 표시하도록 설계한다.

## 1. 목표와 단계 구성

Phase 6은 다음 네 단계로 나눈다.

1. **P6-1 교체 계보**: Item 상세 페이지에서 기존 Replacement Line 관계를 읽어 부모·본인·자식을 보여준다.
2. **P6-2 재구매**: 재구매 날짜와 수량, 현재 보유 수량을 기록하고 교체 시점을 계산한다.
3. **P6-3 점검**: 착용 기록이 없거나 오랫동안 입지 않은 Item을 하나의 `점검` 신호로 모은다.
4. **P6-4 세탁 관리**: 손세탁·드라이클리닝 대상과 완료 기록을 관리한다.

네 단계의 결과는 다음 화면에 함께 반영한다.

- Item 목록: 가장 우선순위가 높은 관리 배지 1개
- Item 상세: 해당하는 관리 배지 전체와 단계별 상세 영역
- More → Maintenance: `점검`, `교체`, `손세탁`, `드라이클리닝`별 대상 목록

## 2. 공통 원칙

### 2.1 원본 사건과 계산값을 분리한다

- 착용은 기존 Wear Log를 원본으로 사용한다.
- 재구매는 별도의 구매 사건으로 기록한다.
- 손세탁·드라이클리닝 완료는 별도의 관리 사건으로 기록한다.
- 배지와 Maintenance 대상 여부는 저장된 상태값이 아니라 원본 사건에서 계산한다.
- Item 목록, Item 상세, Maintenance 페이지는 동일한 공통 계산 함수를 사용한다.
- 날짜 경과만으로도 상태가 바뀔 수 있으므로 현재 로컬 날짜를 포함해 화면 조회 시 다시 계산한다.
- 구매일과 관리일은 시간대 변환이 필요 없는 달력 날짜 사건으로 취급한다.

### 2.2 Retired 처리

- `Retired` Item은 네 종류의 관리 배지를 모두 표시하지 않는다.
- Maintenance 페이지에서도 제외한다.
- Item 상세에서는 Replacement Line과 과거 구매·관리 이력을 계속 표시한다.
- Retired 부모·자식도 Replacement Line에서 제외하지 않는다.
- 새로운 `재구매 기록`, `손세탁 완료`, `드라이클리닝 완료` 버튼은 숨긴다.
- 진행 상태는 현재 관리 신호처럼 표시하지 않는다.
- 잘못 입력한 과거 구매·관리 사건의 수정·삭제는 확인 절차를 거쳐 허용한다.

### 2.3 이번 Phase에서 하지 않는 일

- 운영체제·브라우저 푸시 알림, 예약 작업, 외부 알림
- 일반 세탁기 세탁 기록
- 세일 레이더
- 수량 변경 이력, 입출고 사건, 수량 자동 증감, 본격적인 재고 관리
- 현재 수량을 다른 계산·배지·DB 값과 연동하는 기능
- Item별 세탁 방식 수동 재정의
- 점검 신호 숨김, 완료, 미루기
- Maintenance 페이지의 빠른 처리 버튼
- Notion의 재구매 이력, 수량, 마지막 세탁일 자동 이관

## 3. P6-1 교체 계보

### 3.1 목표

기존 Replacement Line DB의 확정된 관계를 Item 상세 페이지에서 읽기 전용 계보로 보여준다. 새 관계를 만들거나 편집하는 기능은 Phase 4의 기존 흐름을 사용한다.

### 3.2 위치와 표시 순서

Item 상세 페이지의 전체 순서는 다음과 같다.

1. 기본 정보와 상태
2. 구매일·착용 횟수·마지막 착용
3. 월별 착용 분포
4. Replacement Line
5. 재구매·현재 수량
6. 특수 세탁 관리와 이력
7. 포함된 Outfit

Replacement Line 영역은 `월별 착용 분포` 아래, 재구매·세탁 관리·`포함된 Outfit` 위에 둔다.

### 3.3 계보 구성

- 확정된 직접 부모 전체 → 현재 Item → 확정된 직접 자식 전체를 썸네일로 표시한다.
- 현재 Item은 시각적으로 구분한다.
- 직접 부모가 없는 시작점은 `시작 Item`으로 표시한다.
- 부모나 자식이 많으면 가로 스크롤로 탐색한다.
- 부모·자식 썸네일을 누르면 해당 Item 상세 페이지로 이동한다.
- 관계가 하나도 없으면 Replacement Line 영역 전체를 숨긴다.

### 3.4 선택 이유 표시

- 현재 Item으로 들어오는 관계의 선택 이유만 표시한다.
- 예: `대체 시도`, `온도 세분화` 등 기존 Replacement Line DB의 사유
- 각 선택 이유는 해당 부모 → 현재 Item 관계에 연결해 표시한다.
- 다중 부모인 경우 부모별 선택 이유를 구분한다.
- 현재 Item에서 자식으로 나가는 관계 사유는 자식 Item 상세 페이지에서 보여준다.
- 시작 Item은 들어오는 관계가 없으므로 선택 이유를 표시하지 않는다.

### 3.5 데이터와 오류 처리

- 기존 Replacement Line DB와 기존 `loadEdges` 흐름을 재사용한다.
- 다중 부모와 다중 자식을 모두 지원한다.
- 관계를 불러올 때 활성 Item 필터를 적용하지 않으며 Retired 부모·자식도 계보에 포함한다.
- 새 테이블이나 RPC는 추가하지 않는다.
- 계보 조회가 실패해도 Item 상세의 다른 영역은 정상적으로 표시한다.
- 계보 영역 내부에서만 다시 시도할 수 있는 오류 상태를 제공한다.

## 4. P6-2 재구매와 현재 보유 수량

### 4.1 목표

재구매가 가능한 일부 의류와 속옷류에 한해 구매 주기를 기록하고, 현재 몇 개를 보유하고 있는지 간단한 숫자로 확인한다.

### 4.2 기록할 데이터

하나의 Item은 개별 실물이 아니라 동일 상품 또는 동일 정체성을 가진 묶음을 나타낸다. Wear Log와 교체 주기는 Item 단위로 집계하며, 양말·속옷 한 개씩의 생애주기는 추적하지 않는다.

#### 구매 사건

- 재구매 날짜: PostgreSQL `date`
- 해당 구매에서 산 수량: 1 이상의 정수

구매 사건은 누적 이력으로 보존한다. 기존 Item의 최초 구매일과 모든 구매 사건 중 가장 최근 날짜가 현재 교체 주기의 기준점이 된다.

- 과거 날짜와 오늘은 입력할 수 있고 미래 날짜는 막는다.
- 최초 구매일이 있으면 그보다 앞선 재구매 사건은 저장하지 못한다.
- 최초 구매일이 비어 있으면 과거 재구매 사건을 입력할 수 있다.
- 잘못 입력한 사건은 확인 절차를 거쳐 수정·삭제할 수 있다.
- 수정·삭제 후 가장 최근 구매 사건을 다시 찾아 현재 교체 주기를 계산한다.
- 모든 구매 사건이 삭제되면 최초 구매일을 기준점으로 사용한다.
- 구매 사건의 수정·삭제는 현재 보유 수량을 자동으로 바꾸지 않는다.

#### 현재 보유 수량

- Item에 nullable 0 이상의 정수 필드 하나로 저장한다.
- `미입력`, `0개`, `1개 이상`을 서로 구분한다.
- 현재 수량은 J님이 재고를 직접 확인한 뒤 숫자만 덮어쓰는 수동 snapshot이다.
- 수량 변경 이력이나 입출고 사건은 저장하지 않으며 다른 계산의 원본으로 사용하지 않는다.
- 구매 사건의 수량을 현재 보유 수량에 자동으로 더하지 않는다.
- Item 상세의 재구매·현재 수량 영역에서 PurchaseEvent 생성 없이도 이 숫자만 수정할 수 있다.
- 재구매 기록 폼에서 `재구매 날짜`, `구매 수량`, `저장 후 현재 수량`을 함께 입력한다.
- 재구매 시 구매 사건 생성과 저장 후 현재 수량 변경은 하나의 데이터베이스 transaction으로 처리한다.
- 기존 구조에서 transaction을 보장할 수 없다면 작은 RPC를 사용하며, 클라이언트의 보상 rollback은 원자적 저장으로 간주하지 않는다.
- 현재 수량이 0이어도 별도 품절 배지나 Retired 제안은 만들지 않는다.

### 4.3 교체 계산 기준

Notion의 기존 기준을 앱 계산 규칙으로 옮긴다.

| canonical Category | 교체 조건 |
| --- | --- |
| `Top-T-shirts-innerwear` | 현재 주기 기준일 이후 착용 60회 이상 |
| `Socks` | 현재 주기 기준일 이후 착용 30회 이상 |
| `Innerwear` | 현재 주기 기준일로부터 730일 이상 |

- 교체 방식은 공통 resolver에서 canonical Category를 판정해 Item당 하나만 반환한다.
- `Top-T-shirts-innerwear`는 일반 `Innerwear` 규칙에 중복 매칭하지 않는다.
- 대상 Category의 모든 활성 Item에 자동 적용한다.
- 현재 주기의 기준일은 최초 구매일과 모든 구매 사건 날짜 중 가장 최근 날짜이다.
- `Top-T-shirts-innerwear`와 `Socks`는 기준일이 없으면 모든 Wear Log를 센다.
- `Innerwear`는 기준일이 없으면 교체 신호를 만들지 않는다.
- 재구매일과 같은 날짜의 Wear Log는 새 주기에 포함한다 (`wearDate >= purchaseDate`).
- 재구매 전 Wear Log는 보존하되 현재 주기 착용 횟수에서는 제외한다.
- 수량은 교체 임계값을 배수로 늘리지 않는다.
- 현재 수량은 교체 계산과 배지 판정에 사용하지 않는다.
- `Retired` Item은 제외한다.

### 4.4 Item 상세 영역

다음 중 하나라도 해당하면 재구매 영역을 표시한다.

- 교체 계산 대상 Category이다.
- 현재 수량이 입력되어 있다.
- 재구매 이력이 있다.

영역에는 다음을 표시한다.

- 현재 보유 수량
- 현재 교체 주기의 기준 구매일
- 최근 구매 이후 착용 횟수 또는 경과 일수
- 임계값까지의 진행 상태
- 전체 재구매 이력
- `재구매 기록` 버튼
- 현재 수량만 고치는 단순 숫자 입력

Retired Item에서는 이력과 입력 오류 수정·삭제만 제공하고 신규 재구매 버튼, 현재 진행 상태, 현재 수량 수정 입력은 숨긴다.

## 5. P6-3 장기 미착용 점검

### 5.1 목표

Notion의 `착용 기록 없음`, `점검`, `정리 후보`를 앱에서는 하나의 짧은 `점검` 신호로 통합한다. 판단을 강요하는 처분 알림이 아니라, J님이 Item을 다시 살펴볼 대상을 모으는 기능으로 사용한다.

### 5.2 계산 기준

다음 중 하나에 해당하면 `점검`으로 분류한다.

- 누적 착용 횟수가 0회이다.
- 마지막 착용일로부터 2년 이상 지났다.

추가 규칙은 다음과 같다.

- `Innerwear` Category는 제외한다.
- `Retired` Item은 제외한다.
- 3년 이상을 별도의 `정리 후보` 상태로 나누지 않는다.
- 점검 신호는 현재 날짜, Item, Wear Log에서 매번 계산한다.
- Wear Log 추가·수정·삭제, Category 변경, Retired 변경, 날짜 경과에 따라 자동으로 갱신된다.
- 점검 목록은 완료 처리하는 작업 목록이 아니라 조건이 해소될 때까지 유지되는 계산 결과이다.
- 사용자가 점검 완료, 숨김, 미루기를 기록하는 기능은 만들지 않는다.

### 5.3 근거 표시

Maintenance 카드와 Item 상세에는 다음과 같이 계산 근거를 보여준다.

- `착용 기록 0회`
- `마지막 착용 2년 3개월 전`

## 6. P6-4 손세탁·드라이클리닝 관리

### 6.1 목표

일반 세탁이 아니라 별도 관리가 필요한 Item만 추적한다. Category에서 관리 방식을 자동으로 정하고, 최근 관리 이후 착용 횟수로 필요 시점을 계산한다.

### 6.2 관리 방식 결정

관리 방식은 `없음`, `손세탁`, `드라이클리닝` 중 하나이며 Item별 수동 재정의는 제공하지 않는다. 판정은 하나의 공통 관리 방식 resolver에서만 수행한다.

우선순위를 포함한 규칙은 다음과 같다.

1. canonical Category가 `Bags-made`이면 관리 대상에서 제외한다.
2. 그 외 Category에 `made`가 포함되면 `손세탁`이다.
3. 그렇지 않고 Category에 `Outer`가 포함되면 `드라이클리닝`이다.
4. 그렇지 않고 Category에 `Knitwear` 토큰이 포함되면 `드라이클리닝`이다.
5. 나머지는 관리하지 않는다.

`Knitwear`는 독립 Category가 아니라 `Top-Knitwear`, `Bottom-Knitwear`처럼 실제 Category 문자열에 포함된 특성 표식이다. 따라서 두 Category는 드라이클리닝이고, `Top-Sweater-made`와 `Outer-Cardigan-made`는 `made` 규칙이 우선하여 손세탁이다.

### 6.3 필요 시점 계산

| 관리 방식 | 필요 조건 |
| --- | --- |
| 손세탁 | 최근 관리 이후 착용 5회 이상 |
| 드라이클리닝 | 최근 관리 이후 착용 10회 이상 |

- 관리 이력이 없으면 모든 Wear Log를 센다.
- 관리 이력이 있으면 가장 최근 관리일보다 엄격히 뒤인 Wear Log만 센다.
- 관리일과 같은 날짜의 착용은 새 주기에 포함하지 않는다.
- `Retired` Item은 제외한다.

### 6.4 관리 사건

각 관리 사건에는 다음을 저장한다.

- 관리 날짜: PostgreSQL `date`
- 그 당시의 관리 방식

운영 규칙은 다음과 같다.

- `손세탁 완료` 또는 `드라이클리닝 완료` 버튼을 제공한다.
- 기본 날짜는 오늘이다.
- 과거 날짜는 입력할 수 있고 미래 날짜는 막는다.
- 전체 관리 이력을 보존한다.
- 잘못 입력한 사건은 확인 절차를 거쳐 수정·삭제할 수 있다.
- 수정·삭제 후 가장 최근 사건을 다시 찾아 현재 주기를 계산한다.
- 현재 관리 방식은 현재 Category에서 판정하고 사건 당시 방식은 이력 표시용으로 보존한다.
- 현재 주기의 기준일은 사건 당시 방식과 관계없이 가장 최근 CareEvent 날짜이다.
- Category가 관리 대상이 아니게 되면 신호와 입력 영역을 숨긴다.
- 다시 관리 대상 Category가 되면 보존된 가장 최근 CareEvent를 기준점으로 사용한다.
- Notion의 `Last Washed Date`는 자동 이관하지 않고 필요한 소수 Item만 J님이 직접 입력한다.

### 6.5 Item 상세 영역

Category 규칙상 관리 대상인 Item에만 영역을 표시한다.

- 자동 판정된 관리 방식
- 가장 최근 관리일
- 최근 관리 이후 착용 횟수
- 임계값까지의 진행 상태
- 전체 관리 이력
- 관리 완료 기록 버튼

## 7. 관리 배지

### 7.1 배지 종류

배지 문구는 다음 네 가지로 고정한다.

- `점검`
- `교체`
- `손세탁`
- `드라이클리닝`

아이콘이나 색상만으로 의미를 전달하지 않고 문구를 항상 표시한다.

### 7.2 Item 목록

- 카드 하단 요약 영역의 오른쪽에 작은 배지 1개를 표시한다.
- 착용 횟수와 최근 착용일은 계속 읽을 수 있어야 한다.
- 여러 신호가 겹치면 다음 우선순위로 하나만 고른다.
  1. `점검`
  2. `교체`
  3. `손세탁` 또는 `드라이클리닝`
- 카드의 접근 가능한 이름에도 현재 관리 상태를 포함한다.

### 7.3 Item 상세

- 기본 정보의 `상태` 아래에 해당하는 배지를 모두 표시한다.
- 배지가 여러 개면 줄바꿈 가능한 형태로 배치한다.
- 목록에서 하나만 보이던 Item도 상세에서는 해당 신호 전체를 확인할 수 있다.

## 8. More → Maintenance 페이지

### 8.1 구조

More 메뉴에 `Maintenance` 진입점을 추가하고 페이지를 네 영역으로 나눈다.

1. 점검
2. 교체
3. 손세탁
4. 드라이클리닝

- 각 영역 제목에 대상 수를 표시한다.
- 같은 Item이 여러 조건에 해당하면 여러 영역에 중복으로 나타날 수 있다.
- 대상이 없는 영역에는 개별 빈 상태를 표시한다.
- 조회 실패와 실제 대상 0개 상태를 구분한다.

### 8.2 카드 내용

각 카드에는 다음을 표시한다.

- Item 썸네일
- Item 이름
- 대상이 된 계산 근거

근거 예시는 다음과 같다.

- 점검: `착용 기록 0회`, `마지막 착용 2년 전`
- 교체: `최근 구매 이후 60회 착용`, `최근 구매 이후 730일 경과`
- 세탁: `최근 손세탁 이후 5회 착용`, `최근 드라이클리닝 이후 10회 착용`

카드를 누르면 Item 상세 페이지로 이동한다. Maintenance 페이지 자체에는 완료·수정 같은 빠른 작업 버튼을 두지 않는다.

### 8.3 정렬 기준

- 점검: `마지막 착용일`, 착용 기록이 없으면 `최초 구매일`을 기준 날짜로 삼아 오래된 순으로 정렬한다. 기준 날짜가 없는 Item은 그 뒤에 둔다.
- 교체: 현재 값 ÷ 임계값의 진행 비율이 큰 순으로 정렬한다.
- 손세탁·드라이클리닝: 최근 관리 이후 착용 횟수가 많은 순으로 정렬한다.
- 모든 동률은 Item 이름순으로 고정한다.

### 8.4 데이터 로딩 경계

- Item 목록에서는 현재 페이지에 표시되는 Item ID의 구매·관리 사건만 일괄 조회한다.
- Maintenance에서는 활성 Item과 계산에 필요한 Wear Log·구매·관리 사건을 일괄 조회한다.
- Item 상세에서만 해당 Item의 전체 구매·관리 이력을 조회한다.
- 카드별 추가 query를 발생시키지 않는다.
- 계산 함수는 공유하되 화면별 데이터 로딩 범위는 분리한다.

## 9. 데이터 구조와 공통 인터페이스

구현 단계에서 필요한 개념 모델은 다음과 같다. 실제 이름과 세부 타입은 기존 프로젝트 규칙을 확인한 뒤 확정한다.

### 9.1 Item 확장

- `currentQuantity`: nullable, 0 이상의 정수인 현재 보유 수량 snapshot
- 수량 변경 이력, 자동 증감, 다른 계산과의 연결은 두지 않는다.

### 9.2 PurchaseEvent

- workspace와 Item 소유 관계
- 구매 날짜: PostgreSQL `date`
- 구매 수량: 1 이상의 정수
- 생성·수정 시각

### 9.3 CareEvent

- workspace와 Item 소유 관계
- 관리 날짜: PostgreSQL `date`
- 사건 당시 관리 방식
- 생성·수정 시각

### 9.4 MaintenanceSignals

공통 계산 결과는 최소한 다음 정보를 제공한다.

- 점검 대상 여부와 근거
- 교체 대상 여부와 근거
- 손세탁 대상 여부와 근거
- 드라이클리닝 대상 여부와 근거
- 목록에서 표시할 최우선 배지
- Item 상세에서 표시할 전체 배지
- 계산에 사용한 현재 로컬 날짜와 주기 기준일

### 9.5 저장과 보안

- 새 테이블이 필요하면 기존 구조로 해결할 수 없는 이유를 먼저 기록한다.
- 모든 구매·관리 사건은 workspace 소유권과 RLS를 적용한다.
- 노출 schema에 새 테이블을 만들면 RLS와 실제 workspace 소유권 정책을 함께 검증한다.
- 구매 사건 추가와 현재 수량 변경은 하나의 데이터베이스 transaction으로 처리한다.
- 기존 구조로 transaction을 보장할 수 없을 때만 RPC를 추가하고, 함수 내부에서도 사용자와 workspace 권한을 검증한다.
- RPC가 필요하면 기존 구조로 해결할 수 없는 이유와 제거 조건을 기록한다.
- 일회성 Notion 이관 로직을 production 기능으로 만들지 않는다.

## 10. 구현 순서

### P6-1 — Replacement Line 상세 표시

1. Item 상세 데이터 로딩 경계를 확인한다.
2. 기존 확정 edge에서 직접 부모·자식을 계산한다.
3. 계보 UI, 선택 이유, 이동, 빈 상태 숨김을 구현한다.
4. 다중 부모·자식과 모바일 가로 스크롤을 검증한다.

### P6-2 — 구매 사건과 현재 수량

1. 기존 Item·Wear Log·구매일 구조를 감사한다.
2. PurchaseEvent와 `currentQuantity` 저장 구조를 확정한다.
3. PurchaseEvent 수정·삭제, 단순 현재 수량 입력, transaction 저장과 이력을 구현한다.
4. 공통 교체 resolver와 최근 구매 기준 착용·경과 일수 계산 및 `교체` 신호를 구현한다.

### P6-3 — 점검 신호

1. 누적 착용 0회와 마지막 착용 2년 기준 selector를 구현한다.
2. Innerwear·Retired 제외를 적용한다.
3. Item 목록·상세·Maintenance에서 동일한 결과를 사용한다.

### P6-4 — 관리 사건과 Maintenance 완성

1. Category 기반 관리 방식 판정 함수를 구현한다.
2. CareEvent 기록·수정·삭제와 주기 계산을 구현한다.
3. 네 종류 배지를 목록과 상세에 연결한다.
4. More → Maintenance 네 영역을 구현한다.
5. 전체 회귀와 모바일·접근성 검증을 진행한다.

## 11. 검증 계획

### 11.1 계산 경계

- 교체: 59/60회, 29/30회, 729/730일
- 점검: 착용 0회, 마지막 착용 2년 직전/도달/이후
- 손세탁: 4/5회
- 드라이클리닝: 9/10회
- 구매 기준일 없음: 착용형은 전체 Wear Log 사용, 날짜형은 신호 없음
- 재구매일과 같은 날 착용 포함, 다음 날 착용 포함
- 관리일과 같은 날 착용 제외, 다음 날 착용 포함
- 최초 구매와 최근 재구매가 함께 있는 경우
- 날짜 경과만으로 730일·2년 경계에 도달하는 경우
- Retired 전환 전후

### 11.2 Category 규칙

- `Bags-made` 제외
- `made` 손세탁
- `Outer` 드라이클리닝
- `Top-Knitwear`, `Bottom-Knitwear` 드라이클리닝
- `Outer-Cardigan-made`, `Top-Sweater-made`에서 손세탁 우선
- `Top-T-shirts-innerwear`와 `Innerwear` 중복 판정 방지
- `Innerwear`의 점검 제외와 730일 교체 적용

### 11.3 사건 기록

- 재구매 날짜·구매 수량·현재 수량 저장
- 현재 수량의 미입력/0/양수 구분
- 현재 수량만 수정해도 PurchaseEvent가 생성되지 않음
- 수량 수정이 교체 계산에 영향을 주지 않음
- 구매 저장 실패 시 부분 반영 방지
- PurchaseEvent 수정·삭제 후 이전 기준일 또는 최초 구매일 복원
- 오래된 PurchaseEvent를 나중에 추가해도 최신 기준일 유지
- 구매 날짜 미래 입력과 최초 구매일 이전 입력 차단
- 관리 사건의 과거 날짜 허용과 미래 날짜 차단
- 관리 사건 수정·삭제 후 최신 주기 재계산
- Category를 손세탁·드라이클리닝·관리 대상 아님 사이에서 변경
- 같은 날짜에 구매·관리 사건이 여러 개 있는 경우의 안정적인 이력 표시

### 11.4 화면 동기화

- Item 목록은 우선순위에 따른 배지 1개만 표시
- Item 상세는 해당 배지 전체 표시
- 같은 Item이 Maintenance 여러 영역에 나타날 수 있음
- 각 화면의 계산 근거가 동일함
- Retired 부모·자식이 Replacement Line에 계속 표시됨
- Retired 상세에서 이력은 보이고 신규 기록 버튼과 진행 상태는 숨겨짐
- 다중 부모의 선택 이유가 각 부모 관계와 연결됨
- Item 목록 페이지네이션 이동 후 현재 페이지 배지가 정확함
- 사건 조회 실패를 빈 이력이나 대상 0개로 오인하지 않음
- 카드별 추가 query가 발생하지 않음
- 모바일 3열 Item 카드에서 배지가 겹치지 않음
- 키보드 탐색과 스크린리더용 이름으로 상태를 확인할 수 있음

### 11.5 회귀 범위

- Closet 필터·검색·페이지네이션
- Item 상세 통계와 월별 착용 분포
- Wear Log 추가·수정·삭제
- Outfit 상세와 포함 Item
- Replacement Line 편집과 확정 관계
- Home 화면의 기존 집계

## 12. 완료 조건

- Item 상세에서 기존 Replacement Line의 직접 부모·본인·직접 자식과 현재 Item의 선택 이유를 확인할 수 있다.
- 재구매 날짜·구매 수량을 기록·수정·삭제하고 전체 구매 이력을 볼 수 있다.
- 현재 보유 수량은 다른 계산과 연동되지 않는 단순 숫자 snapshot으로 입력할 수 있다.
- 재구매 기록과 저장 후 현재 수량은 하나의 DB transaction으로 저장된다.
- 최근 구매 이후 기준으로 교체 신호가 정확히 계산된다.
- 착용 기록 없음과 2년 이상 미착용 Item이 하나의 `점검` 신호로 계산된다.
- Category 규칙에 따라 손세탁·드라이클리닝 방식과 필요 시점이 정확히 계산된다.
- 관리 완료 이력을 추가·수정·삭제할 수 있고 최근 사건 기준 주기가 갱신된다.
- Item 목록은 우선순위 배지 1개, Item 상세는 해당 배지 전체를 표시한다.
- Maintenance 페이지가 네 영역과 계산 근거를 제공하며 Item 상세로 연결된다.
- 모든 계산 화면이 공통 selector를 사용하고 Retired 제외 규칙이 일치한다.
- 주요 경계값, 모바일 레이아웃, 접근성, 기존 기능 회귀 검증을 통과한다.
