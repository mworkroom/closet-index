- 저장 구조와 편집 흐름이 이미 있으므로 데이터베이스나 API는 변경하지 않았다.

## Work Summary - PC Calendar 월 선택

PC Chrome에서 달력 제목을 클릭해도 월 선택 창이 열리지 않는 문제를 확인했다. 기존 모바일의 화살표 클릭 영역을 유지하면서 PC 마우스 클릭에 선택 창 열기 동작을 추가했다.

## Work Completed - PC Calendar 월 선택

- 배포된 PC Chrome 달력에서 제목 중앙을 클릭하면 숨겨진 월 입력에 초점만 이동하는 현상을 재현했다.
- 월 입력의 마우스 클릭에 `showPicker()`를 호출하고 터치 클릭은 기존 네이티브 동작을 사용하도록 했다.
- 테스트에서 마우스 클릭의 선택 창 호출, 터치 클릭의 중복 호출 방지, 연월 변경과 화살표 이동을 확인했다. Calendar 테스트 4개와 빌드가 통과했다.

## Decisions - PC Calendar 월 선택

- 2026-08-02의 모바일 클릭 영역 수정은 화살표의 쌓임 순서와 제목 폭을 조정했으며, 월 입력의 선택 창 호출 로직을 제거하지 않았다. PC에서 제목 중앙이 입력 텍스트 부분을 가리키는 구조가 직접 원인으로 판단했다.
- 기존 CSS와 모바일 터치 영역을 변경하지 않고, 지원하는 브라우저에서 마우스 클릭에만 표준 `showPicker()`를 호출한다. 미지원 브라우저에서는 기존 입력 동작을 유지한다.

## Current Status - PC Calendar 월 선택

수정은 로컬에만 있다. 로컬 PC Chrome에서 화살표의 이전·다음 월 이동과 콘솔 오류가 없음을 확인했다. 브라우저 자동화 화면은 Chrome의 네이티브 월 선택 팝업을 캡처하지 못해 실제 팝업 표시 자체는 화면으로 확인하지 못했다.

## Work Summary - 실제 착용 온도와 추천 여유 범위 분리

Item·Outfit 화면에 표시되는 온도에서 ±2°C 보정을 제거하고 실제 OK 관측 최저·최고 온도만 보여주도록 변경했다. ±2°C는 HOME 추천의 내부 적합성 판단에만 유지해, 화면 숫자를 다시 역산하지 않아도 되게 했다.

## Work Completed - 실제 착용 온도와 추천 여유 범위 분리

- 실제 OK 관측 범위와 추천용 ±2°C 범위를 공통 온도 유틸리티로 분리했다.
- CLOSET 카드, Item 상세, HOME 착장 카드, Outfit 상세 및 추천 설명에는 실제 관측 범위를 표시한다. 한 온도에서만 OK였다면 `26°C`처럼 단일 값으로 표시한다.
- CLOSET의 `오늘 온도` 검색은 실제로 OK였던 정확한 온도만 찾으며, 관측 사이의 빈 구간이나 ±2°C를 검색 근거로 사용하지 않는다.
- HOME 추천·정렬·신규 구매 및 컨텍스트 적합성 계산은 추천용 ±2°C 범위를 계속 사용한다.
- 23°C OK 기록의 ±2°C 추천 범위에 25°C가 포함되더라도, 실제 25°C `더움` 기록이 있으면 착장을 제거하지 않고 경고가 있는 `주의`로 내려가는 회귀 테스트를 추가했다.
- 관련 테스트를 갱신했고 전체 Vitest 652개 통과(7개 skip), 타입 검사·프로덕션 빌드 및 GitHub Pages 산출물 검증을 수행했다.

## Decisions - 실제 착용 온도와 추천 여유 범위 분리

- 관측값은 사실을 보여주는 UI 데이터로, ±2°C는 HOME 추천을 위한 추정치로 구분한다.
- 여러 Item의 실제 관측 범위가 겹치지 않더라도 각 범위의 ±2°C 추천 구간이 겹치면 새 조합 추천에는 사용할 수 있다. 단, 겹치는 실제 범위가 있는 것처럼 UI에 표시하지 않는다.
- 부정 기록은 양의 추천 여유보다 우선한다. 현재 온도의 `더움`·`추움` 기록은 기존처럼 후보를 삭제하지 않고 경고와 하향 정렬에 반영한다.
- 데이터베이스 구조와 저장 데이터는 변경하지 않았다.

## Current Status - 실제 착용 온도와 추천 여유 범위 분리

로컬 코드 수정과 관련 회귀 테스트는 완료됐다. 전체 Vitest, TypeScript 검사, 프로덕션 빌드가 통과했으며 `GITHUB_ACTIONS=true` 환경에서 SPA fallback을 만든 뒤 Pages 산출물 검증도 통과했다. 처음 로컬 기본 base path로 산출물을 검증했을 때는 `404.html` 및 `/closet-index/` base 조건 때문에 실패했지만, 실제 배포 워크플로 순서와 환경으로 재실행해 정상임을 확인했다. 이 작업 환경에는 브라우저 자동화 패키지가 없어 실제 브라우저 화면 검증은 수행하지 못했다.
