# Learning Log — 앱 난이도를 결정하는 것은 무엇인가

- 작성일: 2026-07-26
- 관련 프로젝트: 옷장 앱, 피라미드 앱, 재고관리 앱, 입학요강 앱
- 성격: 옷장 앱 기획서가 아니라, 여러 앱을 만들며 발견한 설계·개발 방식에 대한 학습 기록

## 1. 이번 대화에서 생긴 핵심 질문

옷장 앱의 기술적 규모는 작지 않다.  
하지만 앱의 난이도가 단순히 기능 수나 DB 구조의 복잡도만으로 결정되는 것은 아니었다.

실제로 만든 앱들의 체감은 예상과 자주 반대로 나타났다.

- 어려울 것 같았던 입학요강 앱은 매우 빠르게 완성됐다.
- 간단할 것 같았던 재고관리 앱은 생각보다 오래 걸렸다.
- 피라미드 앱은 코딩 이전에 도메인을 이해하는 데 큰 비용이 들었다.
- 옷장 앱은 기능 규모는 크지만, 이미 잘 알고 있는 개인 시스템을 옮기는 작업이다.

따라서 앞으로 앱의 난이도를 판단할 때는 “화면이 몇 개인가”, “기능이 몇 개인가”보다 **현실의 규칙과 사용 흐름이 얼마나 정리되어 있는가**를 먼저 봐야 한다.

---

## 2. 피라미드 앱이 어려웠던 진짜 이유

피라미드 앱은 도메인 지식이 거의 0인 상태에서 시작했다.

앱을 만들려면 기존 Google Sheets의 계산 규칙만 이해하는 것으로 충분하지 않았다. 회사 시스템, 실적 계산, 기간별 적용 방식, 예외와 우회 규칙 등 평소 관심이 없던 업무 전체를 새로 배워야 했다.

순수하게 이해하는 데만 약 10시간이 들었고, 이해하기 싫어서 미룬 시간까지 포함하면 약 1주일이 걸렸다.

앱을 만들며 다음 문제도 발견됐다.

- 이해했다고 생각한 규칙이 실제로는 틀린 경우가 있었다.
- 구현 도중 기존 방식이 성립하지 않아 우회로를 찾아야 했다.
- 내가 규칙을 정확히 이해하고 설명하기 전에는 AI도 올바르게 구현할 수 없었다.
- 반대로 설명이 정확해진 뒤에는 구현이 빠르게 진행됐다.

피라미드 앱의 핵심 난이도는 코딩이 아니라 다음 순서에 있었다.

```text
도메인 이해
→ 규칙 확정
→ 예외 발견
→ 설명 가능 상태 만들기
→ 구현
```

여기에 최종 사용자가 어머니라는 UX 문제가 추가됐다.

내게는 명백히 버튼처럼 보이는 요소도 실제 사용자에게는 버튼으로 인식되지 않을 수 있었다. 따라서 기능 구현 이후에도 다음 작업이 남았다.

- 버튼을 더 버튼답게 보이게 만들기
- 기능명이 아니라 사용자가 하려는 행동을 문구로 쓰기
- 눌렀을 때 즉각적인 반응과 완료 상태 보여주기
- 디지털 사용 경험이 낮은 사용자의 실제 행동을 관찰하며 수정하기

## 3. 재고관리 앱에서 발견한 다른 종류의 어려움

재고관리 앱은 도메인이 피라미드 앱만큼 낯설지는 않았다. 그런데도 계속 헷갈리는 지점이 나왔다.

원인은 Supabase나 코딩 기술보다 **앱의 핵심 규칙이 내 머릿속에서도 확정되지 않은 상태에서 즉흥적으로 제작을 시작한 것**에 가까웠다.

예:

- 제품의 특성별 사용 주기를 어떻게 계산할 것인가
- 무엇을 기준으로 재고 부족을 판단할 것인가
- 개봉일, 사용량, 사용 횟수 중 무엇을 우선할 것인가
- 계산값과 직접 입력값의 경계를 어디에 둘 것인가
- 어떤 기능이 정말 필요한가

이런 부분이 정리되지 않은 상태에서 앱을 요청하자, AI는 빈칸을 일반적인 방식으로 채웠다.

그 결과 실제로 앱을 사용하며 다음 생각을 반복했다.

> 이 기능은 왜 여기 있지?  
> ChatGPT는 무슨 의도로 이 기능을 넣었지?  
> 내가 했던 어떤 말을 이렇게 해석한 거지?  
> 이 숫자는 어떤 규칙으로 계산된 거지?

즉, 앱을 만드는 시간보다 **이미 만들어진 설계의 의도를 역으로 해독하는 시간**이 더 길어졌다.

재고관리 앱은 이 해독과 수정 과정을 거쳐 현재는 안정화됐다. 이번 경험으로 다음 사실을 알게 됐다.

> AI가 임의로 내린 설계 결정을 나중에 추적하는 것보다, 제작 전에 미정인 규칙을 드러내는 편이 훨씬 싸다.

## 4. 입학요강 앱이 뜻밖에 쉽게 완성된 이유

입학요강 앱은 어렵고 큰 작업으로 예상했지만 매우 빠르게 완성됐다.

이 앱에는 이미 다음 조건이 갖춰져 있었다.

### 4.1 실제로 작동하는 Notion 구조

AI와 Codex가 기존 Notion DB, 속성, 관계, 데이터를 직접 확인할 수 있었다.

따라서 내가 테이블과 API의 기술적 구조를 처음부터 설명할 필요가 없었다.

### 4.2 확정된 반복 업무

내가 평소 작업하는 과정을 순서대로 설명할 수 있었다.

예:

```text
처음에 어떤 셀이나 항목을 연다
→ 무엇을 입력한다
→ 다음 항목으로 이동한다
→ 특정 작업을 반복한다
→ 결과를 Notion에 저장한다
```

이 과정은 이미 수없이 반복한 실제 업무였기 때문에, 규칙을 새로 발명할 필요가 없었다.

### 4.3 명확한 성공 기준

앱이 해야 할 일은 추상적인 “입학요강 업무 개선”이 아니었다.

> 내가 반복하던 구체적인 클릭과 입력을 대신한다.

이 기준이 명확했다.

기술적으로 가장 중요하게 취급된 부분은 앱에 Notion 쓰기 권한을 허용하는 일이었다. 권한 설정은 실제로 중요하지만, 권한만 연결된 뒤에는 이미 존재하는 구조와 확정된 사용 흐름을 구현하면 됐기 때문에 작업이 빠르게 끝났다.

## 5. AI 시대에 사람이 더 중요하게 설명해야 하는 것

이제 AI는 Notion과 Supabase의 일반적인 구조를 이미 알고 있다.

또한 연결된 도구를 통해 실제 DB 구조를 읽고, 테이블을 만들고, relation을 확인하고, 필요한 설정과 코드를 작성할 수 있다.

따라서 내가 반드시 배워서 설명해야 하는 것은 다음이 아니다.

- Supabase 메뉴의 정확한 위치
- API key를 어느 칸에 붙이는지
- foreign key를 만드는 SQL 문법
- RLS 설정 명령
- Notion API의 세부 형식

이런 작업은 플러그인, Codex, AI가 대신할 수 있다.

반면 다음 내용은 여전히 내가 결정하고 설명해야 한다.

- 이 앱으로 실제로 무엇을 하려는가
- 현재 어떤 순서로 일을 처리하는가
- 어느 단계가 반복적이고 불편한가
- 어떤 값은 직접 입력하고 어떤 값은 계산해야 하는가
- 계산 규칙은 무엇인가
- 수정·삭제 시 과거 데이터에 어떤 영향을 줘야 하는가
- 예외 상황에서 어떤 결과가 맞는가
- 결과가 맞다고 판단하는 기준은 무엇인가

정리하면:

```text
기술 구현은 위임 가능
제품의 현실 규칙은 위임 불가
```

## 6. Supabase를 어디까지 알아야 하는가

Supabase 내부를 모두 공부할 필요는 없다.  
설정 위치와 SQL 문법을 직접 다루지 않아도 된다.

하지만 앱 전체를 블랙박스로 두면 재고관리 앱과 같은 혼란이 반복될 수 있다.

최소한 다음은 이해하고 있어야 한다.

```text
어떤 데이터가 어느 테이블에 들어가는가
무엇과 무엇이 연결되는가
버튼을 누르면 어떤 값이 추가·수정·삭제되는가
화면의 통계가 저장값인지 계산값인지
한 데이터를 바꾸면 다른 기록이 함께 바뀌는가
과거 기록이 현재 데이터와 분리되어 보존되는가
```

필요한 Supabase 개념은 깊은 사용법보다 다음 수준의 지도다.

```text
Table
= Notion Database와 비슷한 원본 데이터 묶음

Row
= Notion의 한 항목 또는 페이지

Foreign Key
= 다른 테이블의 한 항목을 가리키는 연결

Junction Table
= 여러 항목과 여러 항목을 연결하는 중간 표

View
= 원본 데이터를 계산·집계하여 보여주는 가상 표

Storage
= 이미지 파일이 저장되는 공간

RLS
= 누가 어떤 데이터에 접근할 수 있는지 정하는 규칙
```

즉, Supabase 전문가가 될 필요는 없지만 **내 데이터가 어디에서 어디로 흐르는지는 설명할 수 있어야 한다.**

## 7. 옷장 앱은 왜 상대적으로 유리한가

옷장 앱은 기술적 규모만 보면 작지 않다.

- 옷 DB
- 착장 DB
- 착용 기록
- 다대다 relation
- 통계
- 이미지
- 날씨 API
- 규칙 기반 필터
- 코디 구성 UI
- Notion 데이터 이전

그럼에도 피라미드 앱이나 재고관리 앱보다 수월할 가능성이 높다.

### 7.1 도메인을 이미 잘 알고 있다

옷장 앱은 남의 업무 규칙을 새로 배우는 일이 아니다.

내가 수년간 실제로 사용해 온 시스템이며, 무엇이 유용하고 무엇이 불편한지 알고 있다.

### 7.2 Notion이 이미 작동 중인 프로토타입이다

Notion 옷장은 약 한 달에 걸쳐 수동 데이터 이전과 수식 설정을 하며 만든 시스템이다.

그 안에는 과거의 결정이 이미 남아 있다.

- DB를 왜 분리했는지
- 무엇과 무엇을 relation으로 연결했는지
- 어떤 rollup을 사용하는지
- 어떤 통계를 중요하게 보는지
- 직접 입력하는 값과 계산하는 값
- 실제로 보는 view
- 수년간 유지된 분류 기준

과거의 모든 결정을 기억하지 못해도 Notion 구조 자체가 기록 역할을 한다.

### 7.3 실제 데이터가 충분하다

빈 앱을 상상하며 요구사항을 발명하는 것이 아니라, 현재 데이터를 앱에서 어떻게 더 잘 꺼내볼지 생각하면 된다.

### 7.4 최종 사용자가 나다

다른 사용자에게 기능을 설명하고 사용법을 학습시키는 비용이 없다.

직접 써보고 이상한 부분을 즉시 알아차릴 수 있으며, 원하는 결과도 바로 판단할 수 있다.

### 7.5 문제의 중심이 명확하다

옷장 앱의 첫 성공 기준은 이미 분명하다.

> 오늘 27도일 때 입을 수 있는 착장을 빠르게 훑어보고 고를 수 있다.

이것만 제대로 작동해도 실사용 가치가 생긴다.

## 8. 그래도 옷장 앱에서 먼저 정해야 할 것

기존 Notion 구조가 있다고 해서 모든 앱 규칙이 자동으로 확정되는 것은 아니다.

Notion에서 할 수 없어서 생각하지 않았던 문제나, 앱으로 옮기며 새로 생기는 결정이 있다.

예:

- 기존 착장을 수정하면 과거 착용 기록도 새 구성으로 보일 것인가
- 과거 착용 당시의 아이템 구성을 별도 보존할 것인가
- `27도에 적합`을 직접 입력할 것인가
- 과거 `OK` 기록을 이용해 자동 계산할 것인가
- 자동 계산값을 사용자가 수정할 수 있게 할 것인가
- 현재 기온, 시간대별 예보, 최고·최저기온 중 무엇을 추천 기준으로 쓸 것인가
- 외출 시간과 귀가 시간의 온도 차이를 어떻게 반영할 것인가
- 비 예보가 어느 정도일 때 `rain_ok = false` 아이템을 제외할 것인가
- Retired 아이템이 포함된 과거 착장을 계속 표시할 것인가
- 착장 이미지를 완성 이미지로 저장할 것인가
- 개별 아이템 이미지를 실시간으로 합성할 것인가
- Notion을 완전히 대체할 것인가
- 일정 기간 Notion과 Supabase를 병행할 것인가

이 항목들은 기술 문제가 아니라 제품 규칙이다.  
AI가 임의로 결정하게 두지 않고, 결정되지 않았다는 사실부터 드러내야 한다.

## 9. 앱 난이도를 판단하는 새로운 기준

앞으로 앱 난이도는 기능 수만으로 판단하지 않는다.

체감 난이도는 다음 요소의 합에 가깝다.

```text
기술적 구현량
+ 미정인 제품 규칙의 양
+ 도메인을 새로 배워야 하는 정도
+ 예외의 수
+ 정답을 검증하는 비용
+ 실제 사용자의 예측 불가능성
+ 기존 데이터 이전의 난이도
```

각 앱을 이 기준으로 보면 다음처럼 설명할 수 있다.

| 앱 | 기술 규모 | 도메인 이해 | 규칙 확정도 | 검증/사용자 변수 | 체감 |
|---|---:|---:|---:|---:|---|
| 입학요강 앱 | 중간 | 높음 | 매우 높음 | 낮음 | 예상보다 쉬움 |
| 재고관리 앱 | 작음~중간 | 중간 | 초기에는 낮음 | 중간 | 예상보다 어려움 |
| 피라미드 앱 | 중간 이상 | 초기 0 | 낮음 | 매우 높음 | 매우 어려움 |
| 옷장 앱 | 중간 이상 | 매우 높음 | 상당 부분 존재 | 낮음 | 규모보다 수월할 가능성 |

핵심은 다음이다.

> 큰 앱이라도 현실 규칙이 이미 확정되어 있으면 빠를 수 있다.  
> 작은 앱이라도 핵심 계산 규칙이 미정이면 오래 걸릴 수 있다.

## 10. 옷장 앱 제작 전에 필요한 준비 방식

입학요강 앱에서 성공했던 방식을 옷장 앱에도 적용한다.

### 10.1 현재 사용 과정을 그대로 설명한다

기획 용어로 정리하려 하지 말고 실제 행동을 순서대로 말한다.

예:

```text
새 옷을 등록할 때 어느 DB를 연다
→ 어떤 필드를 입력한다
→ 어떤 relation을 연결한다
→ 착장을 만들 때 무엇을 고른다
→ 외출 후 어떤 기록을 남긴다
→ 착용 횟수를 어디에서 확인한다
→ 오늘 입을 옷을 찾을 때 현재 어떤 view를 본다
→ 어디에서 막히거나 귀찮아지는가
```

### 10.2 AI가 현재 Notion 구조를 먼저 해석하게 한다

바로 앱을 만들게 하지 않고 다음을 먼저 요청한다.

```text
현재 Notion 구조와 실제 사용 흐름을 비교하여

1. 앱에서도 그대로 유지할 규칙
2. Notion의 한계 때문에 바꿀 부분
3. 현재 구조에서 확인되는 계산 규칙
4. 아직 결정되지 않은 부분
5. AI가 임의로 가정하면 안 되는 부분
6. 데이터 이전 시 깨질 수 있는 relation
7. 각 버튼이 바꾸게 될 데이터

를 정리한다.
```

### 10.3 미정 사항만 결정한다

전체 Supabase 구조를 직접 공부하는 대신, AI가 찾아낸 미정 사항을 실제 사례로 판단한다.

### 10.4 먼저 작은 실사용 흐름을 완성한다

첫 단계에서는 다음 흐름만 완성해도 된다.

```text
오늘 기온 확인
→ 조건에 맞는 기존 착장 보기
→ 하나 선택
→ 실제 착용 기록 저장
→ 착장과 개별 아이템의 통계에 반영
```

이 흐름이 안정된 뒤 코디 만들기, 세탁, 더 정교한 날씨 조건 등을 확장한다.

## 11. 앞으로 AI에게 요구할 개발 원칙

옷장 앱에서는 기능을 임의로 보충하지 않게 한다.

### 원칙 1. 미정 사항을 구현 전에 표시

요구사항에 빈칸이 있으면 일반적인 방식으로 자동 결정하지 않고 질문 또는 `Open Decisions` 목록으로 남긴다.

### 원칙 2. 기능의 출처를 기록

각 기능이 다음 중 어디에서 나온 것인지 설명하게 한다.

- 현재 Notion 구조
- 내가 설명한 실제 사용 흐름
- 기존 데이터에서 발견한 규칙
- 새 앱을 위해 제안한 기능
- 임시 가정

### 원칙 3. 데이터 변화 설명

버튼이나 기능마다 다음을 함께 기록한다.

```text
입력
→ 변경되는 테이블과 필드
→ 자동 계산되는 통계
→ 과거 기록에 미치는 영향
→ 취소 또는 복구 가능 여부
```

### 원칙 4. 저장값과 계산값 구분

화면에 표시되는 숫자가 DB에 직접 저장되는지, View나 query로 매번 계산되는지 명확히 한다.

### 원칙 5. 현재 구조를 먼저 보존

처음부터 더 세련된 일반형 옷장 앱으로 재설계하기보다, 현재 Notion에서 실제로 잘 쓰고 있는 규칙을 우선 옮긴다.

## 12. 이번 학습의 결론

Supabase 플러그인과 AI 도구가 발전하면서 초기의 기술적 걱정은 크게 줄었다.

- 정확한 설정 위치를 찾아 키를 복사하는 일
- 테이블과 relation을 직접 만드는 일
- SQL과 RLS를 처음부터 배우는 일
- Notion 구조를 사람이 일일이 문서화하는 일

이런 작업은 상당 부분 AI에게 맡길 수 있다.

하지만 기술의 진입 장벽이 낮아질수록 오히려 더 중요해진 것은 **내가 원하는 현실의 규칙을 명확히 하는 일**이다.

재고관리 앱에서는 이 규칙이 정리되지 않아 완성된 앱의 의도를 역추적해야 했다.  
입학요강 앱에서는 실제 업무 흐름과 성공 기준이 확정되어 있었기 때문에 빠르게 완성됐다.  
피라미드 앱에서는 도메인을 새로 이해해야 했기 때문에 가장 힘들었다.

옷장 앱은 기능 규모는 크지만 다음 자산이 이미 있다.

- 수년간 사용한 옷장 시스템
- 한 달 동안 직접 만든 Notion 구조
- 실제 relation과 수식
- 충분한 과거 데이터
- 명확한 현재 불편
- 본인이 직접 사용하는 환경

따라서 옷장 앱의 핵심 과제는 Supabase를 공부하는 것이 아니다.

> 현재 Notion과 실제 사용 습관에 숨어 있는 제품 규칙을 꺼내고, AI가 임의로 결정할 빈칸을 개발 전에 줄이는 것.

기술 구현은 AI에게 맡길 수 있다.  
구조까지 통째로 맡기지 않고, 앱의 설계 의도와 데이터 흐름은 계속 내가 소유한다.
